# v2: бот в групповых чатах жильцов, портреты, подсказки оператору, агенты по ролям

Статус: **анализ и план** (2026-11-17), кода нет. Проверен ревью Fable 5.2 по коду vendor/. Видение ментора и решения команды. Что уже есть в стеке
fazer.ai, чего не хватает, готовые open-source решения и порядок работ.

## 1. Что хочет ментор (сценарий)

1. Оператор УК/ОСИ подключает бота не только к личным чатам «жилец ↔ оператор», но и к **групповым чатам
   жильцов**. Бот читает их круглосуточно, в группе ничего не пишет.
2. По сообщениям бот собирает **портрет каждого жильца**: собственник или арендатор, блок/подъезд, частые
   жалобы, интересы, стиль общения. Портретом список не ограничен. По портрету считается **рейтинг жильца как
   потенциального покупателя** продуктов и услуг компании.
3. Бот **подсказывает оператору**, как лучше ответить и что предложить.
4. По команде оператора бот **пишет жильцу в личку** и предлагает продукт.
5. Пример. Жилец пишет в группу: «меня затопили соседи сверху». Бот уже знает о нём: собственник, блок B, раньше
   жаловался на соседей. Оператор получает подсказку: «есть ИИ-юрист по жилищным спорам (проект другой команды),
   предложите». По команде бот пишет жильцу в личку со ссылкой.
6. Бот продаёт **все** продукты и услуги компании, включая разработки других команд потока.
7. В Telegram бот работает как обычный аккаунт с username, а не как бот.
8. Пайплайн из нескольких агентов, у каждого своя роль: советник, психолог, продавец, аналитик, мониторинг.

### Пробелы (чего нет)

1. **Telegram-группы.** Штатный Telegram-канал Chatwoot группы игнорирует (`return unless private_message?`),
   а через публичный API нельзя создать контакт-группу (`group_type` ставит только WhatsApp). Нужен свой мост на
   userbot (см. §5) и, если группы нужно видеть в Chatwoot, патч форка.
2. **Наблюдатель agents не различает авторов в группе.** В транскрипте каждое входящее сообщение подписано
   одной ролью «Cliente» (`src/modules/chatwoot/transcript.ts`, `ROLE_LABEL`), хотя имя автора в нормализованном
   сообщении есть. `set_custom_attribute` со scope `contact` пишет в контакт **диалога** (`src/graph/tools/native.ts`),
   то есть в контакт **группы**. Поэтому профилирование делаем вне agents: читаем вебхуки Chatwoot, где автор есть.
   Ключ профиля — контакт автора. Патчить `transcript.ts` ради этого не стоит, правку vendor пришлось бы сопровождать.
3. **Первое сообщение жильцу.** `agent_nudge` не создаёт диалог (см. таблицу), поэтому первое касание шлёт наш
   сервис через Chatwoot API: создаёт диалог в inbox на контакт автора и отправляет текст, одобренный оператором.
   Дальше отвечает Продавец. `agent_nudge` — только для повторных касаний в существующем диалоге. Окно 24 ч у
   агента на Baileys-inbox выключить явно (`settings.serviceWindow.enabled: false`).
4. **LID вместо номера.** В группах Baileys участник часто приходит как `@lid` без телефона
   (`group_contact_message_handler.rb`: `baileys_sender_lid`). Такому контакту может быть нельзя написать в
   личку — нужен статус «не достижим».
5. **Подсказки оператору.** В agents их нет; делает наш агент «Советник» (§4). Сторонние copilot-решения не
   используем (решение команды).
6. **Агенты по ролям.** В agents минимальный supervisor, подграфы ролей не реализованы (`docs/graph.md`). Роли
   собираем из нескольких агентов и сервисов (см. §4).
7. **Профиль и рейтинг.** Готового open-source решения «групповой чат → портрет → lead score» нет (см. §6).

## 4. Архитектура

```
 WhatsApp-группы ─┐                                    ┌─> Chatwoot: приватная заметка в карточке жильца
 WhatsApp личка ──┼─> Chatwoot (форк) ── вебхуки ─┐    │
                  │                               ▼    │
 Telegram-группы ─┤   tg-userbot (Telethon)   [ очередь задач в Postgres ]
 Telegram личка ──┘   ├─ личка → Chatwoot API-inbox    │        │
                      └─ группы ──────────────────────>┘        │
                                                                ▼
     ┌──────────── сервис profiler: агент «Мониторинг» + агент «Советник» ───────────┐
     │ согласие/opt-out → дешёвый фильтр → извлечение фактов (LLM, структурный вывод) │
     │ → профиль жильца (Postgres, факты с доказательством и датой)                    │
     │ → интерес к продуктам (прозрачный скоринг) → событие «возможность»             │
     └──────────────────────────────────────┬───────────────────────────────────────────┘
                                            ▼
     агент «Советник»: профиль + разделы сайта + подсказка по стилю общения
       → заметка в Chatwoot + личное сообщение оператору со ссылкой на диалог
                                            ▼  команда оператора: метка/макрос `offer_approved`
                                               в Chatwoot → вебхук conversation_updated
     первое касание: profiler создаёт диалог через Chatwoot API и шлёт одобренный текст
     → жилец отвечает → агент «Продавец» (agents, production): база знаний по сайту,
       инструменты «Аналитика», guardrails и проверка фактов как сейчас
       (повторные касания — `agent_nudge` в существующий диалог)
                                            ▼
     `conversion` / исходящие вебхуки → учёт продаж, обратная связь в скоринг
```

### Роли ментора → компоненты

| Роль | Чем является | Почему так |
|---|---|---|
| **Мониторинг** | Свой сервис `profiler`: читает все группы и личку из очереди, собирает и систематизирует данные о жильцах, отдаёт их остальным | Профиль должен лежать в одной базе с правом на удаление и аудитом, ключ — автор сообщения, а не диалог (пробел 2). occurrences/decisions agents работают по диалогам: годятся для тем «по дому», не «по жильцу» |
| **Психолог** | Не отдельный собеседник, а часть профиля: стиль (на «ты»/«вы», коротко/подробно, язык ru/kk, время активности, текущее настроение) + блок подсказки «как говорить» для Советника и Продавца | Отдельный LLM-агент «рядом» с каждым ответом удваивает стоимость и задержку. Стиль меняется медленно, его достаточно пересчитывать при обновлении профиля |
| **Продавец** | Агент agents в режиме production, отвечает в личке. Его цель — привести жильца на нужный раздел сайта. Содержимое сайта — база знаний (RAG), приёмы продаж — в промпте и базе знаний | Переиспользуем уже настроенное: проверку фактов, handoff, debounce, playground и сценарии |
| **Аналитик** | Инструменты: HTTP/MCP к сторонним сервисам (ИИ-юрист другой команды, заявки, биллинг, 1С) | agents уже умеет HTTP/MCP-инструменты с allowlist хостов |
| **Советник (advisor)** | Модуль того же сервиса `profiler`: по событию «возможность» собирает подсказку оператору и доставляет её в два канала. Команда оператора — метка или макрос в Chatwoot, отдельный бот с кнопками не нужен | В agents подсказок оператору нет (пробел 5). Один сервис вместо двух — меньше работы на 3 спринта |

Параллельность: на одно событие независимо работают мониторинг, советник и (по команде) продавец. Связь между
ними — общий профиль и очередь задач в Postgres (`FOR UPDATE SKIP LOCKED`), а не прямые вызовы. Kafka не
нужна; отдельный outbox и pgvector тоже откладываем до реальной нужды. Если понадобится fan-out — Redis Streams
или NATS.

### Профиль жильца (черновик схемы)

- `resident`: id, канал и контакт (WhatsApp или Telegram), имя, дом/блок/квартира, роль (собственник,
  арендатор, неизвестно), **статус согласия** (none / notified / consented / opted_out), достижимость в личке
  (да / нет — LID без номера), даты.
- **Один человек в WhatsApp и Telegram — по умолчанию два профиля.** Склейка по имени даёт ложный профиль и
  утечку чужих фактов. Связать профили может только оператор вручную или подтверждённый номер телефона.
- `fact`: жилец, тип (адрес, роль, жалоба, интерес, событие), значение, **цитата-доказательство и ссылка на
  сообщение**, уверенность, `valid_from` / `valid_to` (факты устаревают: сменил квартиру, продал).
- `style`: обращение, длина, язык, тон, время активности. Без чувствительных категорий (см. §7).
- `interest`: жилец × продукт → балл 0–100, объяснение «почему» и факты-основания. Рейтинг считает прозрачная
  формула поверх фактов, а не «оценка человека» от LLM. Так рейтинг можно объяснить оператору и ментору.
- `opportunity`: событие (затопление, спор с соседями, долг…), продукт, статус (new, hinted, approved, sent,
  converted, rejected).

## 5. Каналы

**WhatsApp.** Группы и личка уже работают через форк Chatwoot (Baileys). Риски: неофициальный клиент; холодное
сообщение жильцу, который писал в группу, а не на этот номер, — классический повод для бана. Меры:
- сообщения в личку **только после команды оператора**, лимит консервативный — единицы в день;
- **номер для чтения групп и номер для отправки — разные**: бан номера-отправителя не отключит чтение групп;
- официальный WhatsApp Cloud API (шаблоны, opt-in) — отдельное решение на потом.

**Telegram — userbot.** Отдельный сервис `tg-userbot` на одном аккаунте с username:
- читает группы, в которых состоит, и личные сообщения;
- личка → Chatwoot через API-inbox: так же, как сейчас tg-bridge, но от аккаунта, а не от бота;
- группы → очередь задач → profiler (в Chatwoot — после патча `group_type`, если операторам нужно видеть группы
  там);
- исходящие из Chatwoot (ответ оператора или бота) → отправка от имени аккаунта.

| Библиотека | Состояние (2026-11-17) | Вывод |
|---|---|---|
| Telethon (Python, MIT) | репозиторий на GitHub в архиве, разработка переехала на Codeberg, 1.45.0 — 2026-09-10 | **основной кандидат**: зрелая, Python как остальной наш код |
| Kurigram (форк Pyrogram, LGPL-3.0) | активен | запасной вариант |
| mtcute (TypeScript, MIT) | активен | если мост пишем на TS рядом с agents |
| TDLib (официальная, BSL-1.0) | активна | самая надёжная, но тяжелее в сборке |
| Pyrogram, GramJS | **в архиве** | не берём |
| feel90d/chatwoot-messenger-gateway | Telethon + Chatwoot, 15★, последний коммит 2025-08 | взять идеи кода моста, не зависеть от него |
| mautrix-telegram (AGPL-3.0) | активен, мост Telegram ↔ Matrix | образец «puppeting» (сообщения от имени аккаунта), не для прямого использования |

Риски userbot: Telegram ToS и антиспам (`PEER_FLOOD`, заморозка аккаунта), особенно при первых сообщениях
людям не из контактов. Меры: отдельный номер, прогрев аккаунта, лимиты отправки, отправка только по команде
оператора, сессия хранится как секрет (как сессия WhatsApp). **Telegram Business** (позже): официально и без
риска бана, ответ от имени аккаунта с Premium, уже поддержан в Chatwoot. Но работает только в личных чатах, группы
не читает, и первым писать нельзя.

## 7. Согласие, данные, этика (решает ментор; механизм делаем мы)

- **Закон РК № 94-V** «О персональных данных и их защите» (с поправками 2025–2026, в том числе ст. 19-1 об
  автоматизированной обработке и Цифровой кодекс с 12.07.2026). Сбор и профилирование по сообщениям группы —
  обработка ПДн. Отправка текстов в зарубежную LLM — трансграничная передача. Нужна юридическая проверка по
  актуальному тексту на adilet.zan.kz: мы не юристы.
- Механизм в коде с первого дня:
  - реестр согласий;
  - бот официально представлен в группе, правила группы ссылаются на обработку данных;
  - **opt-out одной командой** (в личке или в группе). После неё факты жильца удаляются, новые сообщения не
    обрабатываются;
  - срок хранения;
  - журнал, кто и когда смотрел профиль.
- Минимизация: не извлекаем здоровье, религию, национальность, политику и финансовое положение сверх
  «есть долг по ЖКХ» из наших же систем.
- Рекомендуемое правило по умолчанию: **нет согласия — нет профиля** (а не «профиль, пока не отказался»).
  Окончательно решает ментор.
- «Психологический портрет» — это **стиль общения** (§4). Не используем давление, страх, ложную срочность и
  уязвимость человека (горе, болезнь, пожилой возраст) как рычаг продаж. Это правило попадает в промпты
  Продавца и Советника и проверяется сценариями.
- Тестовая среда — **только синтетические данные**: тестовые группы из аккаунтов команды, сгенерированная
  переписка. Реальные домовые чаты — после решения ментора.

## 8. Модели и стоимость

Чтение групп 24/7 на бесплатных моделях не выдержит: лимиты 429 уже мешают даже проверке фактов (см.
SETUP.md).

Грубая оценка на одного оператора (20 групп × 100 жильцов). Активность реальных чатов нужно замерить:
- 20 групп × 50–200 сообщений в день = **1 000–4 000 сообщений в день**;
- после дешёвого фильтра в LLM-извлечение уходит 10–30%, пачками по жильцу: **~100–600 вызовов в день**,
  по ~1–2 тыс. токенов → **~0,2–1,2 млн входных токенов в день** на оператора;
- подсказки и диалоги Продавца — единицы и десятки в день, по объёму малы.

С ростом числа операторов это растёт линейно, поэтому фильтр и пакетная обработка обязательны с первого дня.
Снижаем так:
- дешёвый фильтр до LLM: ключевые слова (ru и kk), эмбеддинги, классификатор `decisions`;
- пакетная обработка по жильцу раз в несколько минут (debounce, как в agents);
- извлечение — быстрая модель, советник и продавец — сильная;
- жёсткий дневной бюджет токенов; при 429 и исчерпании бюджета — видимая деградация (очередь растёт, алерт), а
  не тихая потеря фактов.

Нужны кредиты (грант Google → Gemini, см. GOOGLE-GRANT-REQUEST.md) и оценка объёма у ментора.
